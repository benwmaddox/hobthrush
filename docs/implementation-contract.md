# M1 pure types implementation contract

This document records the bounded language slices and implementation contracts; it does not complete the full M1 gate in the PRD. The compiler must continue to reject unsupported constructs. All 47 fixture manifest entries are active.

## File ownership

- **Frontend/model:** `src/Lang/Syntax.cs` and `src/Lang/Parser.cs`. Own lexer, parser, source AST, `Range`, `Diagnostic`, and `Token`. Do not edit driver, semantic checker, or emitter files.
- **Semantics/backend:** `src/Lang/Semantics.cs` and `src/Lang/Emitter.cs`. Own typed IR, `Compiler.Check`, and C# emission. Do not edit frontend or driver files.
- **Driver/tests:** `src/Lang/Program.cs`, fixtures, examples, README, and `docs/diagnostics.md`. Remove the old definitions transferred to frontend and semantics. Keep the CLI entry point and fixture runner. Do not edit frontend or semantics files.

These files share a namespace (the current global namespace). The driver owner must remove the old types in `Program.cs` when new files are ready, without changing their public handoff names. Coordinating that one deletion avoids duplicate definitions during parallel work.

Keep `Lexer.Scan(string source, string file, List<Diagnostic> diagnostics)` and `new Parser(tokens, file, diagnostics).Parse()` returning `ParsedProgram?`. The parser reports syntax failures as diagnostics, not exceptions to the driver. It accepts the implemented subset plus `bool` literals, quoted `Text` literals, nested types (`Option<i32>`, `Result<Text, E>`), function type-parameter declarations, union declarations with zero, positional (`Value(i32)`), or named (`TooLong(max: i32)`) payload fields, qualified declaration references, and match expressions with `=>` arms. A variant may not mix positional and named fields. It continues to require explicit `effects {}` on functions. Module paths and source declaration references use `::`; top-level `import` declarations are syntax errors.

The reusable source declaration reference is `SourceDeclarationRefSyntax(Root, Module, Declaration, At)`. Unqualified references have a null root and empty module list; qualified references have a root plus module segments and a final declaration segment. The same representation is carried by `TypeSyntax.Reference`, `CallExpr.Reference`, `StructConstructExpr.Reference`, and `DeclarationRefExpr.Reference`; qualified union patterns carry it in `VariantPattern.Union`. A qualified user union constructor is `self::app::main::Choice.Value(3)`; a zero-payload constructor is `self::app::main::Choice.Yes`, represented as a declaration reference followed by a member access. A match arm accepts `self::app::main::Choice.Yes`, `self::app::main::Choice.Value(value)`, `Some(value)`, `None`, `Ok(value)`, `Err(error)`, or `_`. The parser emits a `VariantPattern` with null `Union` for short builtin patterns. Unqualified `Some`, `None`, `Ok`, and `Err` always denote built-in constructors; a user function with one of those spellings requires a qualified reference and does not shadow the short form. Built-in constructors resolve only when an expected `Option<T>` or `Result<T,E>` type is available from an explicit local annotation, return type, or call parameter. Syntax `Option<i32>.Some` and `Result<T,E>.Ok` is deferred. Pattern bindings are identifiers; payload field names belong to the union declaration and need not match bindings.

Identifier recognition is contextual. Any token of lexical kind `id` is a lexical identifier. The parser's bare-name helper accepts lexical identifiers except exactly `true`, `false`, `null`, `match`, `if`, and `await`. These six retain their current literal, match, or unsupported-expression handling and are excluded from bare declaration/type-root/function/call/binding/unqualified-pattern names. Other keyword-like spellings, including `route`, `return`, `struct`, `pub`, and `with`, are allowed in ordinary name positions; grammar dispatch still recognizes syntax keywords in declaration and statement positions, and top-level `route` enters the checked route grammar.

Member-name positions use lexical identifiers without the bare-name exclusion: struct field declarations and initializer labels, union variant declarations and named payload labels, and identifiers after `.` in field access, variant construction, and qualified patterns. Module and declaration-reference segments also use lexical identifiers. This policy permits forms such as `struct S { return: i32, route: Text }`, `value.if`, `self::app::main::Choice.null`, and `module route::if;`. A bare `null` remains a type mismatch rather than a name.

## Bounded collection and iteration contract

The built-in `List<T>` is recognized contextually in an unqualified type position; a qualified user declaration named `List` resolves normally. List literals are immutable and homogeneous, and `[]` requires an expected `List<T>`. `length` returns `i32`; `get(i32)` returns `Option<T>` with `None` for negative and high indexes; `append(T)` returns a new list value and leaves the original unchanged. `Text.split(Text)` uses an exact delimiter, preserves empty fields, and returns a singleton list containing the original text when the separator is empty. Resource handles cannot be stored in a list or a rebindable `var` local.

`for item in list` visits each item in order. The item is scoped to the body and immutable, calls in the body contribute to inferred effects, and a loop is not considered guaranteed to execute for return-flow analysis. `var name: T = value;` permits rebinding that local to a value of the same type. `let` and loop bindings remain immutable. This is the narrow binding/rebinding decision for the collection slice; it does not settle general mutation, aliasing, identity, equality, parameter copying/sharing, closure behavior, or resource ownership. `Map<K, V>`, index syntax or assignment, list mutation, `break`, and `continue` remain unsupported.

## Checked route declarations

A single-file `lang check FILE` treats the file as a route-capable root. The checked route contract accepts static `GET` and `POST` routes, a path text beginning with `/` and containing none of `{`, `}`, `?`, or `#`, and exactly one fully qualified handler reference. `GET` handlers have no request-body parameter. `POST` routes declare exactly one fully qualified, non-generic struct body type, which is the handler's first parameter. Either handler form may then accept optional `FsWrite`, `DbRead`, and `DbWrite` capabilities in that order; `FsRead` is not supported on web routes. Handlers are non-generic functions returning a declared union. Route body and handler items precede response mappings. Routes with the same method and case-insensitively equal paths are duplicates; different methods may share a path.

Each union variant has exactly one response mapping. Status codes range from 100 through 599. A zero-payload variant has no content format; payload-bearing responses cannot use 1xx, 204, 205, or 304 statuses. A single-payload variant uses `json Type` or `html`; JSON accepts `i32`, `bool`, `Text`, or a fully qualified user struct whose fields recursively use those scalar types. Recursive structs and other unsupported shapes are rejected. The stated JSON type must equal the union payload type. `html` requires an opaque `Html` payload. Source code can construct `Html` with the contextual builders `html.text(Text)`, `html.heading(Text)`, `html.paragraph(Text)`, `html.concat(Html, Html)`, and `html.document(Text, Html)`; text inputs are escaped, and there is no raw-markup insertion API. Handler references use normal qualified-name resolution and visibility checks.

Route declarations are checked into route IR in single-file checks and in the entry module of a `kind = "web"` package. A web package requires an `entry_module` containing at least one route and `[capabilities] net.listen = "allow"`; only that root entry module may declare routes. Paths are static and only `GET`/`POST` are supported; path and query parameter binding are not implemented. A root web package may grant `fs.write`; database grants require SQLite configuration. Route handlers receive only signature-requested opaque capabilities in `FsWrite`, `DbRead`, `DbWrite` order after any POST body; `FsRead` is not supported on web routes. Web packages build and run as managed ASP.NET applications, and `lang run PACKAGE -- --urls URL` forwards the host URL option. Generated output includes a deterministic `openapi.json` beside the managed DLL. The host accepts JSON request bodies up to 1 MiB, returns 400 for malformed or incompatible JSON and 413 for larger bodies, returns 404/405 for unmatched paths/methods, and maps unexpected handler faults to a generic JSON 500 with a request ID. The grants are compiler-checked metadata, not a sandbox. Web packages do not support Native AOT. The maintained [`examples/web`](../examples/web) sample uses a configured SQLite database, idempotent schema, a transaction-scoped write, the shared validation library, and safe Html builders. Source-level asynchronous handlers and cancellation remain unimplemented; the adapter does not complete M2 or V1.

For SQLite-enabled web packages, the conditional managed dependency is pinned to `Microsoft.Data.Sqlite` 10.0.12. Startup applies the UTF-8 schema file to the configured database; `LANG_SQLITE_PATH` overrides the database file at run time. Route handlers receive optional `FsWrite`, then `DbRead` and `DbWrite`, after any POST body, with required grants checked against the root manifest; `FsRead` is not supported on web routes. `DbRead.query_one` takes a source string literal and a concrete parameter struct, statically accepts only one `SELECT` with no semicolon, and requires an explicit `Result<Option<FullyQualifiedRow>, DbError>` expected type. Its provider connection is read-only and enables SQLite `query_only`. `DbWrite.execute` and `Transaction.execute` take a SQL source literal and a concrete parameter struct and return `Result<i32, DbError>`. Parameter and row structs must contain only `i32`, `bool`, `Text`, or `Option` of those scalar types. Parameters bind by `$field`; row columns must have exactly the expected names and count, scalar SQLite types, and nullability. A missing row returns `Ok(None)`; a second row, duplicate/missing/extra column, wrong scalar type, or NULL in a required field returns `Err(DbError.RowShape)`. SQLite statement errors return `Err(DbError.Statement)`.

The only transaction form is `with db.begin() as tx { ... }`, which requires `db.write`. The checker permits `tx` only as the direct receiver of `execute` or `commit` inside that body; aliasing, passing, returning, storing, using it in a generic wrapper, or other receiver uses report `E_RESOURCE_ESCAPE`. `Transaction.execute` accepts a single literal `INSERT`, `UPDATE`, `DELETE`, or `REPLACE` statement with no semicolon; transaction-control, DDL, and other statements report `E_DB_TRANSACTION_STATEMENT`. `tx.commit()` returns `Result<bool, DbError>` and succeeds once with `Ok(true)`. A failed execute marks the transaction rollback-only; a later commit returns `Err(DbError.Statement)`. On scope exit, disposal rolls back unless that first commit succeeded, including normal fallthrough and early function return. The transaction can execute writes only; reads remain on the separate read-only `DbRead` path. This is a narrow resource-scope rule and does not establish general ownership/borrowing semantics. Adapter operations still block from source code, so language-level async handlers and cancellation control remain incomplete. Web packages without SQLite configuration do not emit the SQLite package reference.

## Checker and backend handoff

Keep Compiler.Check(string file, string source) -> CheckResult, CheckResult(CheckedProgram? Program, List<Diagnostic> Diagnostics), and Emitter.Emit(CheckedProgram program, bool executable = true) -> string. On any diagnostic, Program is null. CheckedProgram contains Module, Functions, Unions, Structs, and the checked Routes IR; its function collection contains CheckedFunction values. CheckedFunction exposes Name, Parameters, and ReturnType where ReturnType is a resolved semantic type with DisplayName (for example i32 or Option<i32>) and IsI32, IsBool, and IsText. The driver recognizes an executable entrypoint by name main, zero parameters, and a return type whose resolved semantic type reports IsI32, IsBool, or IsText. The emitter consumes only typed IR, never Expr, Stmt, or TypeSyntax source nodes. Every typed expression carries its resolved type and source token; typed variant and match nodes carry resolved union/variant identities and bound payload locals.

The checker supports `i32`, `bool`, `Text`, opaque `Html`, immutable non-generic nominal structs, declared non-generic unions, compiler-known `Option<T>` and `Result<T,E>`, and generic functions. `Html` is built only through the contextual safe `html.text`, `html.heading`, `html.paragraph`, `html.concat`, and `html.document` builders; there is no raw-markup insertion API. Generic function type arguments are inferred from independently typed call arguments; each declared type parameter must occur in a function parameter type. The current slice has no explicit type arguments, generic structs or unions, traits, or constructor-driven inference. In particular, a direct `Some` or `None` expression passed to a generic call retains `E_TYPE_MISMATCH` because no concrete expected `Option<T>` is available. Generic parameters are valid as values and supported type-constructor arguments, but operations requiring a concrete type remain rejected. The checker also checks exact assignment/return/argument types, arity, payload types, match scrutinee type, duplicate or invalid variants, arm result type agreement, and exhaustiveness. A source wildcard covers remaining variants only when explicitly written. Arithmetic `+`, `-`, `*` accepts only `i32` and emitted arithmetic remains checked. Comparisons are `==`, `!=`, `<`, `<=`, `>`, `>=`: equality accepts matching `i32`, `bool`, or `Text`, while ordering accepts `i32`; comparisons return `bool`. `if` conditions must be `bool`, branch scopes are independent, and a function is guaranteed to return only when a return statement is reached or both branches of an `if`/`else` return. `E_UNREACHABLE` marks a later statement after a guaranteed return. `Text.length` returns an `i32` Unicode scalar count, and `Text.trim()` removes leading and trailing Unicode whitespace per the pinned runtime. `null` yields `E_TYPE_MISMATCH`; unknown types or names fail compilation. A function that can fall through retains `E_TYPE_MISMATCH` with `Function must end with a return value`. `E_MATCH_NONEXHAUSTIVE` identifies each omitted variant at the match span. Type errors use `E_TYPE_MISMATCH` with expected and actual type names. The backend emits deterministic C# from resolved semantic types and does not infer types from source spelling.

## Driver contract

All check, build, and run commands call Compiler.Check before doing backend work. lang check FILE --json returns schema version 1 with an empty diagnostics array on success; --json is check-only. Missing files and expected file/process failures produce diagnostics instead of an unhandled exception.

lang build FILE emits an executable if the checked program contains a supported zero-argument main returning i32, bool, or Text, or one typed command declaration. Otherwise it emits a library, including when a function named main has a different signature. A typed-command build also writes deterministic `command-schema.json` beside its executable. It stages generated projects in unique temporary directories, removes staging output after the build, and copies durable artifacts to a unique out/<source-stem>-<id>/ directory beside the source file. The compiler and generated projects explicitly set `ServerGarbageCollection=false`, selecting Workstation GC.

The optional Native AOT deployment form is `lang build FILE_OR_PACKAGE --aot --rid RID`. It applies only to a checked executable source with a supported zero-argument `main() -> i32|bool|Text` or one typed command declaration, or a CLI package with that main entry or one typed command declaration; library-only sources and packages and the compiler tool are not AOT targets. The supported RIDs are `win-x64` and `linux-x64`, and the build host OS must match the RID (`win-x64` on Windows, `linux-x64` on Linux). Cross-OS publishing is unsupported and reports `E_BUILD_TARGET`. A matching .NET Native AOT native toolchain is required. The SDK publish output is staged before the native executable is copied to the unique durable output directory as `Generated.exe` on Windows or `Generated` on Linux. Typed-command builds also copy their deterministic `command-schema.json` beside the native executable. Success prints `Built native executable: <absolute path>`; SDK publish output, including Native AOT compatibility warnings, is forwarded to stderr as unstructured text. A successful publish does not guarantee that no warnings were emitted. Normal `lang build FILE_OR_PACKAGE` and `lang run FILE_OR_PACKAGE` retain the managed output path. Native AOT remains GC-managed and does not change source semantics. Shared-library exports are outside this command and remain in the separate ABI1 proof.

Use `E_BUILD_TARGET` when a recognized `--aot` or `--rid` option is missing a required companion, malformed, or used outside the exact build form; when the RID is unsupported; or when the checked program lacks the supported executable entrypoint. The diagnostic messages are:

- Missing or malformed options after `--aot`: `lang build --aot requires --rid RID (supported RIDs: win-x64, linux-x64)`
- Unsupported RID: `Unsupported AOT runtime identifier '<rid>'; supported RIDs: win-x64, linux-x64`
- RID targets a different OS than the current build host: `NativeAOT runtime identifier '<rid>' targets a different OS than the current host; cross-OS publishing is not supported`
- AOT options used outside the exact form: `The --aot and --rid options are only valid with lang build FILE_OR_PACKAGE --aot --rid RID`
- No supported executable entrypoint: `lang build --aot requires fn main() -> i32, bool, or Text with no parameters, or a command entry`

General malformed CLI invocations that do not use a recognized AOT option keep normal usage handling.

lang run FILE requires a supported main unless its command arguments are supplied with `--`, in which case a typed command entry is dispatched. Main runs write one line containing the returned i32, lowercase bool, or Text value and exit 0. Checked i32 arithmetic overflow prints a generic runtime-fault message to stderr and exits 70. Diagnostics include E_ENTRYPOINT, E_IO, E_PROCESS, E_BUILD, E_BUILD_TARGET, E_TYPE_VISIBILITY, and E_MATCH_ARM_DUPLICATE.

## Struct values contract addendum

This addendum extends and supersedes the `ParsedProgram` handoff shape above: its final constructor parameter is `IReadOnlyList<StructDecl> Structs`, after `Functions`. The rest of the existing parser and checker contracts remain in force.

The exact additional source AST records are:

```csharp
internal sealed record StructFieldDecl(string Name, TypeSyntax Type, Token At);
internal sealed record StructDecl(string Name, bool Public, IReadOnlyList<StructFieldDecl> Fields, Token At);
internal sealed record StructFieldValue(string Name, Expr Value, Token At);
internal sealed record StructConstructExpr(
    Token At, string Name, IReadOnlyList<StructFieldValue> Fields) : Expr(At);
internal sealed record FieldAccessExpr(Token At, Expr Target, string Field) : Expr(At);
```

Structs are immutable, nominal, and non-generic. Empty declarations and constructions are legal. Field declarations have unique names. Each construction names every declared field exactly once; extra or repeated initializers are rejected. The checker reports `E_FIELD_UNKNOWN` for an undeclared initializer or read, `E_FIELD_DUPLICATE` for a repeated initializer, `E_FIELD_MISSING` for an omitted field, and `E_TYPE_MISMATCH` for an incompatible field value. Initializer expressions are evaluated in source order, independent of declaration layout. Public structs and their public field types obey the existing public-type visibility checks.

A field read may follow a local, call result, parenthesized expression, or struct construction and may chain through nested structs. Methods are unsupported. A no-call dotted expression whose target is a qualified union declaration reference remains the zero-payload union constructor form. Locals shadow value names in dotted field access and dotted-call syntax; local member calls are unsupported rather than treated as variant construction.

The parser does not consume a struct construction as an unparenthesized top-level match scrutinee, because the next `{` begins match arms. Parenthesize the construction explicitly; for example, `match (self::app::main::Box { value: self::app::main::Choice.Yes }).value { self::app::main::Choice.Yes => 1, self::app::main::Choice.No => 0 }`. Other match scrutinees retain their existing grammar.

Direct cycles made only of struct fields are rejected with `E_TYPE_MISMATCH`. A recursive path passing through `Option`, `Result`, or a tagged union is allowed. This is a direct-layout rule, not a general recursive-type or ownership system.

The acceptance set adds active fixtures 22-25 for recursive wrapper values, field type mismatch, duplicate/unknown/missing initializers, and bare recursion. The runnable `examples/structs` program exercises nested and reordered initializers, `Option`, a tagged union, and chained field reads. This slice does not complete M1 or the V1 promise; generic structs and unions, explicit type arguments, traits, other application capability grants, additional adapters, capability-backed web features, and the complete maintained application set remain separate work. The maintained scan CLI demonstrates the bounded `fs.read` command grant.

## Package modules contract addendum

Package commands accept a package directory: `lang check PACKAGE_DIRECTORY [--json]`, `lang build PACKAGE_DIRECTORY`, `lang run PACKAGE_DIRECTORY`, `lang lock PACKAGE_DIRECTORY`, and `lang audit PACKAGE_DIRECTORY --json`. The root manifest requires `name`, `version`, `kind`, and `source_root`, plus `entry_module` for CLI and web packages. A CLI entry module may contain the supported zero-argument `main() -> i32|bool|Text` or one typed command declaration; main-based CLI packages retain their existing contract. CLI manifests may grant `fs.read` and/or `fs.write`; web manifests require `net.listen` and may also grant `fs.write`. Capability grants accept only the exact string value `"allow"`. SQLite-enabled web manifests declare both normalized package-relative file paths `sqlite_path` and `sqlite_schema`. Database grants are valid only for web packages and require both paths; schema configuration also requires `db.write` for startup initialization. Libraries cannot declare application capabilities, but library source may expose checked functions that accept `DbRead` or `DbWrite` without database paths or grants; a library using database operations receives the conditional SQLite provider reference when built. The optional `[dependencies]` table maps language identifier aliases to relative package paths, one assignment per line; all values are plain double-quoted strings. Blank lines and comments outside quoted values are accepted; escapes are not. `kind` is `lib`, `cli`, or `web`. The package name must be filesystem-safe, the version string must be non-empty, `source_root` must be a normalized forward-slash relative directory within the package, and `entry_module` must be a valid `::`-separated module name such as `app::main`. Libraries omit `entry_module`; CLI and web packages provide it. Web packages require a route in the entry module and are managed-only. The dependency alias `self` is reserved; remaining aliases are case-insensitively unique. Paths are resolved relative to their declaring manifest, and every target must be a library package. Different package roots cannot use the same name and version. Manifest file, schema, key, value, and invalid dependency path errors report `E_MANIFEST` or `E_DEPENDENCY`; a missing required `net.listen` grant reports `E_CAPABILITY_MISSING`.

The loader recursively discovers `.lang` files under each package's `source_root`. A relative path with the extension removed and directory separators replaced by `::` must exactly match the source's `module` header. For example, `src/app/main.lang` declares `module app::main;`. A mismatch, invalid module path, or duplicate module path within the same package reports `E_MODULE_PATH`. Module identities include the package root, so equal module paths in different dependencies remain isolated. Each source has one module header followed by declarations; there is no source-level import declaration, and legacy top-level `import` syntax fails with `E_SYNTAX`. Every user declaration reference names a root, one or more module segments, and a declaration separated by `::`: `self::text::validation::normalize` selects the current package, while `validation::text::validation::normalize` selects a directly declared dependency alias. The alias `self` is reserved. User declarations must be qualified even within their declaring module; short forms remain available for built-ins, type parameters, and local values. Module and declaration segments use contextual identifier rules. The `.` separator remains for value fields, member operations, and union variants, such as `self::catalog::message::Message.Ready(value)`. A qualified reference to a private declaration outside its declaring module reports `E_ACCESS_PRIVATE`; an unknown alias, module, or declaration reports `E_NAME_UNRESOLVED`. Aliases are direct to one package and are not re-exported. Qualified union patterns participate in exhaustiveness checking, so adding a variant can produce `E_MATCH_NONEXHAUSTIVE`.

Path dependencies are local filesystem references and work offline. Git sources, registries, dependency caches, `lang add` or other package-install commands are not implemented. Package audit and successful-build receipt contracts are defined below. `lang lock` resolves the complete local graph and writes deterministic JSON to the root `lang.lock`. The lock records the root's name, version, and normalized manifest hash; dependencies have relative paths from the root, name, version, normalized content hash, and their direct dependency aliases. Content hashes cover the manifest and `.lang` sources of dependency packages. Dependency source line endings are normalized, and `out/` files are not inputs. Lock paths are portable relative paths and contain no workspace-specific absolute paths. A nonempty dependency graph must have a current canonical lock before `check`, `build`, or `run`; missing, malformed, or stale locks report `E_LOCK`. Running `lang lock` creates or updates the file. Dependency-free packages do not need a lockfile.

For `kind = "cli"`, the named entry module must be discovered and must define exactly one supported zero-argument `main() -> i32|bool|Text` or one typed command declaration. A missing entry module or unsupported/missing executable entry reports `E_ENTRYPOINT`; duplicate same-module declarations retain `E_NAME_DUPLICATE`. A `main` in a non-entry module does not select the package entrypoint. Libraries may contain ordinary functions named `main` but have no package entrypoint. A command handler requesting `FsRead` or `FsWrite` must have the matching `fs.read` or `fs.write` manifest grant; its capability parameters follow generated arguments in `FsRead` then `FsWrite` order. For `kind = "web"`, the named entry module must exist and contain a route; route handlers use the checked static route contract and normal effect checking. The managed host maps JSON payloads and declared response variants, writes deterministic `openapi.json` beside its executable DLL, accepts a 1 MiB maximum request body, and emits a generic JSON 500 with an `X-Request-Id` on unexpected handler faults. HTML text builders escape content. `lang run WEB_PACKAGE -- --urls URL` forwards the host URL option. Web package builds use Workstation GC and ASP.NET Core and are not Native AOT targets; `lang build PACKAGE_DIRECTORY --aot --rid RID` reports `E_BUILD_TARGET` for web packages.

The maintained `examples/library-package` acceptance example contains a main-based CLI entry module that uses qualified references for public functions, structs, and unions in its own package, then calls generic `require` through its sibling `text-validation` path dependency. Integration acceptance also covers deterministic lock creation, missing/malformed/stale lock rejection and refresh, normalized source hashing, graph validation, direct alias visibility and module identity, public and private access, unknown aliases/modules/declarations, unqualified user references, legacy import and dotted-module rejection, module-path/header mismatches, manifest schema rejection, main and typed command entrypoint rules, JSON diagnostic locations, qualified-union exhaustiveness, managed builds, package AOT argument rejection, and the managed language-test runner. The runner typechecks tests in dependencies but executes only root-package tests, requires current dependency locks, continues after assertion failures, and reports stable module/source locations. It has no JSON runtime result format, property framework, or AOT test runner. This slice supports local offline package paths only: Git or registry sources, caches, and package-install commands are deferred. Package audit and successful-build receipt contracts are specified in the audit contract below.

## Control flow and Text contract addendum

Function bodies support `if condition { ... }` with an optional `else { ... }`. Conditions have type `bool`. Each branch starts from the enclosing immutable local scope and branch declarations do not escape. An `if` guarantees a return only when it has an `else` and both branches guarantee a return. A statement after a guaranteed return reports `E_UNREACHABLE`; a function that can fall through reports `E_TYPE_MISMATCH` with `Function must end with a return value`.

Expression precedence from highest to lowest is unary minus, multiplication, addition/subtraction, ordering comparison (`<`, `<=`, `>`, `>=`), then equality (`==`, `!=`). Operators at each binary level are left-associative. Equality requires operands of the same supported scalar type (`i32`, `bool`, or `Text`); ordering requires `i32`. There are no boolean conjunction or disjunction operators in this slice.

`Text.length` returns the number of Unicode scalar values as `i32`, so a supplementary character counts once. `Text.trim()` takes no arguments and uses the pinned .NET runtime's Unicode whitespace trimming. These operations and control flow support the PRD's `examples/text-validation` package shape. That pure library package is a precursor; the final maintained validation library still needs broader source support.

## Effect and filesystem capability addendum

Every function retains a mandatory `effects { ... }` annotation. Its entries come from the closed vocabulary `fs.read`, `fs.write`, `process.spawn`, `net.client`, `net.listen`, `db.read`, `db.write`, `env.read`, `clock.read`, `log.write`, and `secret.reveal`; annotations are upper bounds on inferred effects. The checker propagates effects through direct and qualified calls and recursive call cycles. `E_EFFECT_EXCEEDED` reports the shortest known path to an effectful operation. `E_EFFECT_UNKNOWN` and `E_EFFECT_DUPLICATE` reject unknown and repeated entries.

Implemented operations include `FsRead.read_text(path) -> Result<Text, FsError>` (`fs.read`), `FsWrite.write_text(path, value) -> Result<bool, FsError>` (`fs.write`), `DbRead.query_one` (`db.read`), and `DbWrite.execute`, `DbWrite.begin`, `Transaction.execute`, and `Transaction.commit` (`db.write`). Both filesystem operations accept a `Text` or `FilePath` path; `write_text` takes a `Text` value. `FsRead` and `FsWrite` are opaque capabilities that source code cannot construct. `FsError` has exactly five zero-payload variants: `NotFound`, `PermissionDenied`, `InvalidPath`, `InvalidText`, and `Io`; source code cannot construct these variants, and the read and write adapters produce them. Matches must be exhaustive unless they explicitly use `_`. The read adapter reads bytes from the supplied path and decodes them using strict UTF-8. The write adapter encodes the complete value as strict UTF-8 without a BOM, creates and flushes a unique temporary file beside the destination, and then calls `File.Move` with overwrite enabled. The destination is staged before replacement; whether overwrite-rename is atomic depends on the host OS and filesystem. Embedded NUL and path-related `ArgumentException`, `NotSupportedException`, or `PathTooLongException` map to `InvalidPath`; missing file or parent directory maps to `NotFound`; `SecurityException` and `UnauthorizedAccessException` map to `PermissionDenied`; encoder fallback maps to `InvalidText`; and other `IOException` failures map to `Io`. A leftover temporary file is removed best-effort. `FsWrite` uses host OS path resolution and does not confine writes to a package root or provide a filesystem sandbox. SQLite uses literal SQL with concrete parameter/row structs and strict row decoding; reads are limited to one `SELECT` and zero-or-one rows, and transaction writes to one literal DML statement. These adapter internals are trusted, not proven by effect checking, and capability checks are not a process security boundary.

Library functions may receive `FsRead`, `FsWrite`, `DbRead`, or `DbWrite`, and effectful managed libraries can be built. A `cli` package can grant `fs.read` and/or `fs.write`; the generated command entry injects only requested, granted capabilities after its generated arguments, in `FsRead` then `FsWrite` order. A configured `web` package requires `net.listen` and may grant `fs.write` plus configured `db.read` and/or `db.write`; its route entry injects only requested capabilities after the optional body, in `FsWrite`, `DbRead`, `DbWrite` order. `FsRead` is not available to web routes. Missing grants or capability values report `E_CAPABILITY_MISSING`, and manifest grant changes are covered by lock freshness. The narrow compiler-derived `lang inspect effects` and `lang inspect api` reports and the schema-v1 package audit and build receipt are defined below. The current filesystem and SQLite operations are bounded, synchronous V1 adapters; async/cancellation and the remaining effect adapters are future work. Adapters remain trusted boundaries; these reports do not establish a sandbox or prove adapter internals safe. This remains a bounded M2 implementation, not M2 completion.

## Inspect effects contract addendum

`lang inspect effects PACKAGE_DIRECTORY SYMBOL --json` checks the package graph and inspects one root-package function. `SYMBOL` must use the fully qualified `self::module::function` form. Inspection requires a current lock when the package has dependencies. Malformed command usage follows the normal usage path; an unsupported, malformed, or unresolved symbol returns structured `E_NAME_UNRESOLVED`. Package, lock, or compiler diagnostics stop the command before any effects report is emitted.

The successful JSON report uses schema version 1 and contains `symbol`, `declared_effects`, `inferred_effects`, `effect_paths`, `required_capabilities`, `manifest_grants`, and `trusted_operations`. Each `effect_paths` item contains an effect name and an ordered `steps` array giving the shortest known route from the inspected function to that operation. The root function step is `module::function`; dependency function steps use stable `name@version::module::function` labels and never include filesystem paths. Package name and version are independently encoded as UTF-8 percent-encoded components: RFC 3986 unreserved bytes remain literal, and all other bytes use uppercase hexadecimal escapes. This prevents separators, control characters, and path syntax in manifest values from becoming label structure. `required_capabilities` describes capabilities required by the function's inferred effects; `manifest_grants` describes grants configured on the root package. These fields are distinct: an unused grant can appear in `manifest_grants` without appearing in `required_capabilities`.

Trusted operations are emitted in deterministic order. A typed CLI handler reports `cli.argument_decode` and `cli.output` as `trusted_host` operations with no language effects. A function whose inferred effects include `fs.read` reports `FsRead.read_text`; `fs.write` reports `FsWrite.write_text`; `db.read` reports `DbRead.query_one`; and `db.write` reports the reachable `DbWrite`/`Transaction` operation names as `trusted_adapter` operations with the corresponding effect. This metadata is compiler-derived; it does not prove the host or adapter implementation safe or establish a sandbox. The package audit and build receipt preserve these trust declarations as claims; see the next contract section.

## Inspect API contract addendum

`lang inspect api PACKAGE_DIRECTORY --json` resolves and checks the complete root package graph, then emits a compiler-derived public API and checked application-surface report. A current `lang.lock` is required when the root has dependencies, using the same lock rules as package checks. The exact command form requires `--json` as its final argument. Malformed usage prints the normal usage line to stderr and exits 2. Invalid package paths, graph/lock failures, and package diagnostics use the existing JSON diagnostic envelope `{ "schemaVersion": 1, "diagnostics": [...] }` on stdout and exit 1; no API object is emitted on failure. Success emits the API object on stdout and exits 0.

The successful report has `schema_version: 1` and exactly these top-level fields in addition to it: `package`, `dependencies`, `manifest_grants`, `functions`, `structs`, `unions`, `commands`, and `routes`. `package` is `{ alias, name, version }` for the root, with alias `self`; the `package` field on declaration records uses the same shape. `dependencies` contains one `{ alias, name, version }` record for every direct root dependency alias, sorted by alias; two aliases to the same package remain two dependency records. `manifest_grants` is the root manifest's configured grant-name array, sorted ordinally. It records configuration rather than inferred effects or verified trust claims.

The `functions` array includes each public function from the root package and its directly declared dependencies once. A function record has `id`, `source_ids`, `package`, `type_parameters`, `parameters`, `return_type`, `declared_effects`, `inferred_effects`, `effect_paths`, `calls`, and `required_capabilities`. Each type parameter is `{ name, ordinal }`, where ordinal is zero-based; each parameter is `{ name, type }`. An effect-path record is `{ effect, steps }`; steps follow the shortest checked call path and end with `{ kind: "operation", name }`. A function step has `{ kind: "function", source_id, source_ids, package, module, name }`. Each `calls` item is a structured identity for one resolved direct call: `{ source_id, source_ids, package, module, name }`. Calls are direct edges, not the transitive call closure. Function `required_capabilities` is derived from the function's inferred effects and reports the modeled `fs.read`, `fs.write`, `db.read`, and `db.write` requirements. `declared_effects` describes the function's declared upper bound; `inferred_effects` describes compiler analysis of its body and callees.

The `structs` array contains public root/direct structs with `{ id, source_ids, package, fields }`; each field is `{ name, type }`. The `unions` array contains public root/direct unions with `{ id, source_ids, package, variants }`; each variant is `{ name, payload }`, where each payload item is `{ name, type }` and `name` is null for a positional field. Field, variant, payload, parameter, and type-parameter arrays preserve checked source order.

The root `commands` array contains `{ id, package, help, inputs, handler, handler_source_ids, error_formatter, error_formatter_source_ids, error_type, required_capabilities }`. Each input is `{ name, kind, type, help, default_value }`, where `kind` is `argument`, `option`, or `flag`; `default_value` is null or `{ kind, value }`, with `kind` equal to `text`, `i32`, or `bool`. Handler and formatter names use canonical source IDs, with their complete usable aliases in the corresponding `*_source_ids` array. The command requirement reports each checked handler capability: `fs.read` and/or `fs.write`.

Each `routes` item has `{ method, path, body_type, handler, response_type, handler_source_ids, responses, required_capabilities, capability_parameters }`. `body_type` is null or a type. `response_type` is a nominal union reference with `{ kind: "nominal", declaration_kind: "union", source_id, source_ids, package, module, name }`; a transitive reply union retains package identity with null `source_id` and empty `source_ids`. Each response is `{ variant, status, content_type, payload_type }`; content type is `json`, `html`, or null, and a payload type may be null. Each capability parameter is `{ name, capability }`. Route `required_capabilities` lists checked `fs.write` and database capability parameters, sorted by capability name; `capability_parameters` preserves handler parameter order and identifies each parameter. The root web grant such as `net.listen` remains in `manifest_grants`.

Types are recursive JSON objects. A primitive is `{ kind: "primitive", name }`, with names `i32`, `bool`, `Text`, `Html`, `FilePath`, `FsRead`, `FsWrite`, `FsError`, `DbRead`, `DbWrite`, `Transaction`, or `DbError`. A type parameter is `{ kind: "type_parameter", name, ordinal }`. A list is `{ kind: "list", item }`, an option is `{ kind: "option", item }`, and a result is `{ kind: "result", ok, error }`; nested values use this same type encoding. A user struct or union is `{ kind: "nominal", declaration_kind: "struct"|"union", source_id, source_ids, package, module, name }`. For every nominal type, direct call target, and effect-path function, `package` is `{ name, version }`. Source-facing declaration IDs are fully qualified as `alias::module::declaration`; the root uses `self`, and a directly depended-on package uses one of its root manifest aliases. `id` and `source_id` use the ordinally first usable alias; `source_ids` contains every usable direct alias in ordinal order. For a transitive nominal type, call target, or effect-path function, `source_id` is null and `source_ids` is empty, while `package: { name, version }`, `module`, and declaration `name` retain stable identity without a filesystem path. This report describes direct root visibility and does not add source-level imports, transitive alias re-exports, or source access to transitive dependencies.

The output is deterministic: dependencies sort by alias; `source_ids` by alias; manifest grants and capability sets ordinally; declaration arrays by canonical `id`; direct calls by `source_id` (empty when null), package name, package version, module, then declaration name; and effect arrays and paths by the closed effect vocabulary. Shortest effect-path ties use stable package name/version/module/function identity followed by source line and column, never package or source paths. Nested declaration contents retain checked source order, and routes sort by method then path. Successful output contains no absolute package or source paths. The report has no trusted-operation or trusted-claim fields. It describes compiler-checked declarations, effects, calls, and application metadata; `lang audit` and build receipts add package input hashes and explicit trusted-host/adapter claims. Neither report proves adapter behavior or creates a security sandbox.

## Audit and build receipt contract

`lang audit PACKAGE_DIRECTORY --json` resolves and checks the complete root package graph. A current `lang.lock` is required when dependencies exist; the lock validates resolution but is not itself listed as a hashed report input. The exact command requires `--json` as its final argument. Usage errors print the normal usage line to stderr and exit 2. Invalid paths, graph or lock failures, package diagnostics, and input-hashing failures print the existing diagnostic envelope `{ "schemaVersion": 1, "diagnostics": [...] }` on stdout and exit 1; no partial audit object is emitted. Success writes deterministic UTF-8 report JSON with a final LF to stdout and exits 0.

The successful report uses schema version 1 and has these top-level properties in serialization order: `schema_version`, `packages`, `compiler`, `manifest_grants`, `trusted_claims`, and `foreign_dependencies`. `packages` contains every resolved node, sorted by package-relative path. Each record is `{ identity, role, content_sha256, dependencies, inputs }`; `identity` is `{ name, version, path }`, where the root path is `.` and dependency paths are relative to the root with `/` separators. `role` is `root`, `direct`, or `transitive`. Each dependency is `{ alias, package }`, sorted by alias, with a full package identity. Each input is `{ kind, path, sha256 }`, sorted by normalized relative path. Inputs include `lang.toml`, every discovered `.lang` source under `source_root`, and, when configured, the SQLite schema (`kind: "sqlite_schema"`).

Each input's `sha256` is SHA-256 over strict UTF-8 text after converting CRLF and CR line endings to LF. `content_sha256` is a domain-separated, length-delimited SHA-256 over the package inputs in path order, including their normalized relative paths and normalized text. Thus line-ending-only changes retain the same digest, and package identities/input paths contain no workspace-specific absolute paths. Packages sort by relative path; dependency and manifest-grant names, function facts, effects, calls, effect paths, and trust claims use ordinal deterministic ordering by their stable relative identities.

`compiler.functions` includes each checked function from every package in the graph, including private functions. Function records are ordered by package-relative path, module, and name, and contain `package`, `module`, `name`, `visibility`, `declared_effects`, `inferred_effects`, `effect_paths`, `direct_calls`, and `required_capabilities`. `package` is `{ name, version, path }`; visibility is `public` or `private`. Declared, inferred, and required-capability arrays sort ordinally; effect paths sort by effect. An effect path is `{ effect, steps }` and ends in an `{ kind: "operation", name }` record; function steps identify `{ kind: "function", package, module, name }`. Each `direct_calls` item is `{ package, module, name }`; these are distinct resolved direct edges ordered by target package path, module, then name. `required_capabilities` maps the modeled `fs.read`, `fs.write`, `db.read`, and `db.write` effects. These are compiler inferences; `manifest_grants` separately lists only the root manifest's configured grants, sorted ordinally. A configured grant is not evidence that a function requires it or that the operation is secure.

Each `trusted_claims` record has `{ operation, source, effects, assurance, reachable_from }`, ordered by `source` then `operation`; claim effects sort ordinally and reachable function identities sort by package path, module, then name. `source` is `trusted_host` or `trusted_adapter`, and `assurance` is exactly `claim_only`. The current host claims are `cli.argument_decode` and `cli.output` (no effects), `web.net_listen` (`net.listen`), `web.request_decode` and `web.response_output` (no effects), and configured `web.schema_init` (`db.write`). Adapter claims name reachable `FsRead.read_text` (`fs.read`), `FsWrite.write_text` (`fs.write`), `DbRead.query_one` (`db.read`), `DbWrite.execute`, `DbWrite.begin`, `Transaction.execute`, and `Transaction.commit` (`db.write`). `reachable_from` contains `{ package, module, name }` function identities for the root entry, command/route handlers, or, when no such root exists, public root functions that reach the adapter operation. The claim records describe compiler-recognized integration points only; they do not inspect or verify host/adapter internals, establish a sandbox, or amount to a formal proof.

`foreign_dependencies` is distinct from the language package graph. Each record is `{ name, version, ecosystem, reason }`; it currently lists pinned `Microsoft.Data.Sqlite` version `10.0.12` with `ecosystem: "nuget"` and `reason: "generated_build"` when configured SQLite or checked database effects require that provider; it does not enumerate a general .NET/NuGet dependency closure.

A successful `lang build` for a standalone source or package writes `build-receipt.json` after managed build or Native AOT publish succeeds and artifacts have been copied. `lang run`, `lang check`, and `lang test` do not write one. The receipt is deterministic UTF-8 JSON with a final LF and schema version 1. Its properties, in serialization order, are `schema_version`, `build`, `package_graph`, `toolchain`, `inputs`, `manifest_grants`, `trusted_components`, `foreign_dependencies`, `audit_snapshot_sha256`, and `artifacts`:

- `build` is `{ mode, framework, runtime_identifier }`; `mode` is `managed` or `native_aot`, `framework` is `net10.0`, and `runtime_identifier` is null for managed builds or the requested RID for AOT.
- `package_graph` is an empty array for a standalone source; for a package, it lists `{ identity, role, content_sha256, dependencies }` records in the same path order as the audit `packages` array. Each dependency is `{ alias, package }`, sorted by alias; identities are `{ name, version, path }` with relative paths.
- `toolchain` is `{ compiler_version, compiler_sha256, dotnet_sdk_version, foreign_dependencies }`. The compiler hash is over the compiler assembly bytes. Its foreign dependency list repeats the top-level list.
- `inputs` lists package inputs with `{ package, kind, path, sha256 }`, ordered by package-relative path then input path. A standalone source has one record with `package: null`, `kind: "source"`, `path: "source"`, and its normalized source hash.
- `manifest_grants` lists root grants; `trusted_components` contains the same explicit claims as `trusted_claims` in the audit report; `foreign_dependencies` uses the audit dependency records.
- `audit_snapshot_sha256` hashes the exact serialized schema-v1 package audit JSON bytes, or the standalone checked snapshot for a source build. The receipt contains this digest rather than embedding the whole snapshot.
- `artifacts` lists files under the output directory as `{ path, sha256 }`, sorted by relative path using `/`; the receipt itself is excluded.

Receipt paths are relative, and schema v1 includes no timestamp, output-directory GUID, or absolute path. Its hash inventory is an audit record, not a claim that generated binaries are reproducible. It does not certify runtime or integration tests, adapter behavior, security, or formal bounds; a passing build and a claim-only trust entry do not prove those properties. The current receipt binds compiler analysis through `audit_snapshot_sha256` rather than separately enumerating checks or embedding every effect fact.

## Typed CLI command contract addendum (PR1)

A `cli` package entry module supports either its existing zero-argument `main() -> i32|bool|Text` or one typed command declaration. Existing main-based CLI packages retain their current behavior. The PR1 command form is:

```lang
command scan {
    help "Scan a path.";
    argument input: FilePath help "Path to scan.";
    option limit: i32 = 1 help "Maximum work items.";
    flag recursive help "Include child paths.";
    handler: self::app::main::run;
    error: self::app::main::describe_error;
}
```

Command items may appear in any order. A command requires exactly one command-level `help`, `handler`, and `error`, at least one positional argument, and no more than one command in the executable entry module. Argument, option, and flag names are contextual identifiers. Their supported types are `FilePath`, `Text`, and `i32`; option defaults must be literals of the matching type. `FilePath` is opaque to source and decoded by the CLI parser.

For a command named `scan`, the compiler generates the public nominal `ScanArgs` type in the entry module. The fully qualified handler function must accept that type and return `Result<Text, E>`. When a CLI package grants `fs.read` and/or `fs.write`, the handler may accept optional `FsRead` then optional `FsWrite` parameters after its generated arguments; the command entry injects only the capabilities requested by the checked signature. A missing required grant reports `E_CAPABILITY_MISSING`. The fully qualified error formatter must accept the same `E`, return `Text`, and be pure. Handlers retain ordinary effect declaration and inference checks. Only CLI packages may declare the supported grant; standalone sources and library packages cannot. Version-2 command schemas list granted capabilities required by each handler and injected by the trusted command entry, in parameter order; the list may contain `fs.read`, `fs.write`, or both, and unused manifest grants are omitted. Grant changes participate in lock freshness.

`lang run FILE_OR_PACKAGE -- APPLICATION_ARGS` forwards arguments after the separator to a typed command entry. Main-based source and package runs do not accept this separator. Within command arguments, a standalone `--` ends option parsing and lets following positional values begin with `-`, for example `lang run PACKAGE -- scan -- --leading`. Top-level `--help` and `scan --help` exit 0. Unknown commands, unknown options, missing positional arguments, missing option values, duplicate options, invalid `i32` values, and empty or NUL `FilePath` values print `CLI_UNKNOWN_COMMAND`, `CLI_UNKNOWN_OPTION`, `CLI_MISSING_ARGUMENT`, `CLI_MISSING_VALUE`, `CLI_DUPLICATE_OPTION`, and `CLI_INVALID_VALUE`, respectively, and exit 2. Control characters in diagnostic subjects are escaped to keep the message on one physical line. `Ok(Text)` writes the returned text to stdout and exits 0. `Err(E)` is passed to the formatter, written to stderr, and exits 3. Unexpected runtime faults exit 70.

Managed and Native AOT builds of standalone sources or packages with a typed command emit deterministic UTF-8 `command-schema.json` beside the executable artifact, with a final LF. Its version-2 JSON uses snake_case property names and declaration/source order for argument, option, and flag arrays. Command records contain the command name and help, fully qualified handler and formatter references, the handler-required injected capability list, and arrays describing each input; defaults are native JSON string or integer values and flag records have type `bool`. The maintained `examples/scan-cli` package demonstrates the bounded FsRead grant and typed runtime mapping. The schema-v1 package audit and successful-build receipt are implemented; adapters beyond the current filesystem and bounded SQLite operations remain future work.
