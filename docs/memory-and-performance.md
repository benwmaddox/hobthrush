# Memory semantics and performance evaluation

This contract records the accepted .NET implementation baseline, the completed MS1 source contract, and the decisions that remain open outside MS1. It informs [the PRD](PRD.md) and [the roadmap](roadmap.md); it does not implement a runtime or benchmark suite. The language is pre-1.0: source and serialized contracts may change without backward-compatibility or migration support. Schema numbers identify the current format for tooling and tests; compiler, tests, documentation, and examples move together when that format changes.

## Accepted V1 commitments

- Keep the compiler bootstrap/build tool in C#, emit C#, and use the pinned .NET SDK/runtime. A later hob-authored compiler does not require replacing the first-party runtime.
- Use the .NET GC-managed runtime with Workstation GC as the V1 default, explicitly selected for the compiler and generated applications. Native AOT remains GC-managed under the same policy. Scoped resource handles (such as files, transactions, and response bodies) require deterministic cleanup on success, error, and cancellation; garbage collection is not resource-scope cleanup.
- The bounded list slice treats list values as immutable. `append` returns a list value with the new element and does not change the original; the current C# emitter lowers `List<T>` to `System.Collections.Immutable.ImmutableArray<T>`. Workstation GC remains the selected V1 runtime policy; the emitted collection representation is an implementation detail and creates no source-level layout or ABI promise.
- The bounded `Bytes` value owns a private immutable octet sequence. `append` checks the signed `i32` before narrowing and creates a new snapshot; source code has no backing-storage accessor. Sequence representation and allocation behavior remain implementation details, without a layout, ABI, or performance promise. The numeric slice adds immutable `i64`, `u32`, and `u64` values with explicit decimal suffixes, same-width checked arithmetic, equality, and ordering while preserving eager unsuffixed `i32`; it makes no conversion, codec, ABI, or formal-bounds claim.
- The collection slice makes one narrow binding decision: `var name: T = value;` declares a local that may be rebound to another value of the same type, while `let` and `for` item bindings are immutable. This permits binding reassignment without introducing mutation of list contents. Resource-bearing values cannot be stored in `List` or `Map` values or rebindable `var` locals. Nominal struct and union fields may contain resource handles, and immutable values with non-`Transaction` capabilities may be directly constructed and returned; resource reachability follows actual stored fields and payloads, so an unused phantom type argument adds no resource. Newtypes are opaque nominal wrappers with explicit `wrap` and `.value` projection; a newtype whose actual representation stores a resource handle is rejected, while a phantom resource argument that is not stored remains allowed. MS1 below completes the ordinary-value sharing, equality, and closure decisions; it does not define general ownership semantics for other resource types.
- The SQLite `Transaction` handle has one deliberately narrow lexical rule: it is introduced only by `with db.begin() as tx`, can be used only as the direct receiver of `tx.execute` or `tx.commit` inside the body, and cannot be aliased, passed, returned, or stored. Scope exit rolls back unless the first commit succeeds. MS1 below records this adapter-specific behavior as the current lexical resource contract; it does not define general ownership, borrowing, mutation, or escape behavior for other resource types.
- Define portable source semantics independently of the selected C# representation. A source struct is not promised to be a C# record, class, or value type.
- Generated heap-allocated C# records are a current prototype, not a public allocation, identity, or layout guarantee. Do not restrict source syntax solely to suit a possible lowering.
- Scoped resource checks do not imply a general borrow checker, ownership proof, deterministic execution, real-time behavior, or security sandbox. Keep the foreign/adapter trust boundary explicit.

## MS1: memory-semantics design (complete)

MS1 fixes the source-level contract for the currently supported value and resource forms. It does not promise a C# layout, a borrow checker, general ownership, or observable object identity.

| Area | Decision | Conformance |
| --- | --- | --- |
| Ordinary values | Supported ordinary values are immutable. Assignments, parameters, and returns may share storage; because the values cannot be mutated and identity is not source-visible, sharing and copying are observationally equivalent. `let` and loop bindings are immutable; `var` rebinds only its binding to another value of the same type. Nominal struct and union values may contain non-`Transaction` capability handles and may be returned from ordinary functions. | Fixture 44 checks immutable assignment; fixture 58 checks assignment, parameter/return, and rebinding behavior. |
| Equality | `==` and `!=` use structural equality. `i32`, `i64`, `u32`, `u64`, `bool`, and `Unit` compare by value (`Unit` has one value, written `()`, and equality still evaluates both operands once from left to right); `Text` uses ordinal, non-normalizing comparison; Bytes compare exact octets by length and order. Declared structs and unions compare recursively by fields and variant; nominal newtypes compare recursively through their wrapped representation when it supports equality, without comparing equal to the representation itself. `Option`, `Result`, lists, and maps compare recursively; list order matters, while map entries compare by ordinal Text key and value independent of insertion order. `FilePath` and `Html` compare their wrapped text ordinally; `HttpResponse` compares status and body; `ProcessOutput` compares exit code, stdout, and stderr; built-in error unions, including `BytesError`, compare by variant. There is no reference-identity operator. | Fixture 58, Bytes fixture 105, wide-integer fixture 107, newtype fixture 99, and structural-equality integration cases cover nested values, snapshots, map order, newtype wrappers, and rebinding. |
| Equality exclusions | Resource/capability values and nominal types whose actual stored fields or payloads contain a handle, `Secret<Text>`, and unconstrained generic type parameters do not have structural equality. Bytes and BytesError are ordinary non-resource leaves; a value containing Bytes plus another stored resource remains resource-bearing. A phantom type argument is not resource-bearing unless a stored field or payload uses it. Newtype declarations whose representation actually stores a capability/resource handle are rejected with `E_RESOURCE_ESCAPE`; phantom resource arguments remain admissible. The compiler reports a type mismatch for an equality expression outside the supported set; this does not reject ordinary resource-bearing struct/union declarations or direct immutable values. | Fixtures 59–60 cover generic and resource equality rejection; fixture 105 covers Bytes equality/storage; fixtures 99 and 102 cover newtype structural equality and stored-resource rejection; existing transaction and collection fixtures cover resource escape. |
| Mutation and closures | Source-visible ordinary values have no in-place mutation operation. The implemented closure subset is an immediately invoked, one-parameter, expression-bodied lambda with an explicit parameter type. It captures immutable `let`, parameter, and loop bindings with value semantics; capturing a rebindable `var` reports `E_CLOSURE_CAPTURE_MUTABLE`. Resource-bearing lambda parameters, results, and captured values report `E_RESOURCE_ESCAPE`; unconstrained type parameters are unsupported in parameters, captures, and results. Lambda values cannot be stored or returned; nested and async lambdas are not implemented. | Fixture 61 and integration execution verify immutable capture; fixtures 62–64 and integration diagnostics reject mutable, resource, and generic captures. |
| Scoped resources | The only source-visible scoped handle is `Transaction`, introduced by `with db.begin() as tx`. It has one lexical owner, may be used only as the direct receiver of `execute` or `commit` in that scope, and cannot be aliased, passed, returned, stored, or wrapped. Exit rolls back unless a commit succeeds. Generated cleanup runs on normal completion, returned errors, runtime faults, early return, and cancellation unwinding; rollback ignores request cancellation before transaction/connection disposal. | Transaction runtime integration covers commit, implicit rollback, failed statements, early return, runtime fault, cancellation, and subsequent database work. Negative transaction diagnostics cover alias, pass, store, and wrapped-type escapes. |
| Foreign adapters | Adapter implementations remain trusted runtime code. Their declarations do not prove safety, resource behavior, or effect truth; richer interop ownership contracts are outside this decision. | Adapter behavior is covered only by its explicit integration contracts; no general foreign-safety proof is claimed. |

The limited closure syntax makes the selected capture rule executable without exposing function values or a general ownership system. Generic closure types remain unsupported because an unconstrained type parameter cannot be proven to be an ordinary value. These decisions remain independent of generated C# records, classes, arrays, dictionaries, or any future backend representation.

### Static traits and value semantics

Static traits add compile-time operation selection without introducing a source-level trait object, reference identity, or mutation. A checked implementation is a closed trait/target pair whose methods bind to synchronous, nongeneric, pure functions with the substituted signature. The checker enforces one visible implementation per pair and rejects recursive implementation-obligation cycles; ordinary recursive calls inside a binding remain ordinary function calls. Generic forwarding passes a constrained zero-state witness type, and generated code uses static-abstract interface members with readonly witness structs. The witness has no instance state and is not boxed or allocated for trait dispatch. Resource eligibility follows the actual stored fields or union payloads of the closed target: a phantom type argument does not make an implementation resource-bearing, while a stored resource handle excludes it. Trait dispatch changes neither the sharing equivalence of immutable values nor the structural equality rules above.

Nominal newtypes are explicit wrappers, not transparent aliases. `Newtype.wrap(value)` accepts only the declared representation type, and `.value` is the only representation projection. Conversions, arithmetic, ordering, and trait implementations are never inferred or forwarded; a newtype may participate in an explicitly declared static-trait implementation under the existing coherence and orphan rules. Equality is structural through the representation but preserves the nominal type boundary. Newtype recursion follows the same direct-cycle and guarded-recursion rules as other nominals, and actual stored resource handles are rejected at the newtype declaration.

### MS1 transaction decision record (narrow adapter contract)

This implements only the pre-existing PRD requirement for a source-scoped SQLite transaction. It is an adapter-local exception because the transaction is hidden behind one capability and one lexical scope; the rule does not decide ordinary value semantics or the behavior of other resource types. The SQLite adapter commits to one lexical handle form: `with db.begin() as tx { ... }`. Within that body, `tx` may appear only as the direct receiver of `tx.execute(SQL_LITERAL, Parameters)` or `tx.commit()`. Aliasing it, using it as a local value, passing it as an argument, returning it, storing it in a struct or union payload, placing it in a generic wrapper, or using another receiver/member form is rejected with `E_RESOURCE_ESCAPE`. `Transaction.execute` accepts one literal `INSERT`, `UPDATE`, `DELETE`, or `REPLACE` statement and a concrete parameter struct; semicolons, transaction-control statements, DDL, and other SQL forms are rejected with `E_DB_TRANSACTION_STATEMENT`. This keeps SQL from bypassing rollback-by-default through an embedded `COMMIT`, `ROLLBACK`, or `BEGIN`.

`execute` returns `Result<i32, DbError>`. The first successful `commit` returns `Ok(true)`; a failed statement makes the transaction rollback-only, and a later commit returns `Err(DbError.Statement)`. Repeated or invalid commits also return `Err(DbError.Statement)`. A scope that exits without a successful commit rolls back. The generated managed adapter owns a `Microsoft.Data.Sqlite` connection and `DbTransaction`, disposes them deterministically at scope exit, and relies on provider disposal/rollback behavior. This adapter and its interop remain trusted runtime boundaries; the adapter-specific rule does not define ownership behavior for other scoped resources.

The transaction implementation follows the decision above: the generated lexical scope disposes its adapter on every exit path, and disposal rolls back without consulting the canceled request token before releasing the transaction and connection. SQLite calls remain synchronous; cancellation conformance comes from an async host call while the transaction scope is open, not from a source-level async SQLite API. This rule applies to the current transaction adapter only; other scoped handles and richer foreign ownership contracts require their own design before introduction.

### FsWrite adapter behavior (bounded V1 operation)

`FsWrite.write_text` accepts one complete `Text` value and materializes its full strict UTF-8 byte array before writing. It synchronously stages and flushes a same-directory temporary file, then uses an overwrite move. The operation has no streaming interface, byte quota, or source-level cancellation hook; additional managed memory scales with the encoded value size. This records the generated adapter shape and does not set a performance target.

## PERF1: performance evaluation (not started)

PERF1 measures representative applications without setting a speed, memory, latency, startup, build-time, or published-size target. Use executable CLI workloads and, when available and compatible, web/SQLite applications. Compare the ordinary managed build with an optional Native AOT executable built from the same source and using the same Workstation GC policy on the matching host OS. Native AOT is a deployment publish mode for executable applications only: it requires a supported runtime identifier (RID) and native toolchain, remains garbage-collected, and may reject code or adapters that depend on unsupported dynamic features. Preserve successful publish warnings when recording compatibility limits; these remain unstructured SDK text rather than language diagnostics, and successful publishing is not a no-warning guarantee. The compiler tool and shared-library exports are outside this deployment path; the latter belong to the separate ABI1 proof. This is not a second backend or a runtime rewrite.

Pin the hardware, OS, .NET SDK, RID, native toolchain, workload and input versions. Record commands, warmup, repetitions, and raw results. Measure startup, bytes allocated per operation and collection counts, steady and peak memory, throughput, p95/p99 latency, published size, and build cost. Preserve program behavior in comparisons. Path or line-ending normalization may be narrow and documented; it must not hide behavior or diagnostics differences. Report compatibility limits and unsupported adapters. These measurements support deployment choices; they establish no cross-language comparison or numerical performance guarantee.

PERF1 measurements inform deployment decisions; they are not a numeric performance gate. Continue to meet the three application acceptance gates in the PRD. No formal-proof, hard real-time, or security-sandbox guarantee follows from these measurements.
